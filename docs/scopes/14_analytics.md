# スコープ14: テストケース分析

## 目的

蓄積されたテスト実行と不具合のデータを集計し、進捗と品質の傾向を確認できるようにする。

## 対象要件

- ユーザーはテスト実行ごとの分析を表示できる（消化率 / 合格率 / 結果ごとの件数と割合 / スイート別 / 担当者別 / 日別の推移 / 完了予測日）
- ユーザーはプロダクト単位の分析を表示できる（バージョン別の比較 / 実施履歴の推移）
- ユーザーは不具合の分析を表示できる（ステータス別・重要度別 / スイート別の発生件数 / 起票と解決の推移 / 平均日数）
- ユーザーは繰り返し不合格となっているテストケースを一覧で確認できる
- ユーザーは分析の対象期間・対象バージョンを指定して絞り込みできる
- ユーザーは分析結果をCSVでエクスポートできる

## 前提スコープ

- 13 不具合管理

## 実施内容

### seed定義

| 種別 | 追加するもの |
| --- | --- |
| api_schemas | `TestRunAnalytics`（結果別件数、消化率、合格率、スイート別、担当者別、日別推移、完了予測日）、`ProductAnalytics`（バージョン別の集計、実施履歴）、`DefectAnalytics`（ステータス別・重要度別、スイート別、推移、平均解決日数）、`RepeatedFailureSummary` |
| api_endpoints | `GET /v1/test_runs/{test_run_id}/analytics`、`GET /v1/products/{product_id}/analytics`、`GET /v1/analytics/defects`、`GET /v1/analytics/repeated_failures`、各エンドポイントに対応する `.../analytics/export`（CSV） |
| errors | 対象期間の指定が不正（開始が終了より後） |
| pages | `TestRunAnalytics`、`ProductAnalytics`、`DefectAnalytics` |

### API

- `repository/analytics.rs` を追加し、集計SQLをまとめる
  - テスト実行の集計は `test_run_cases.latest_result_kbn` を使う（スコープ11で保持している最新結果）
  - 日別の推移は `test_results.executed_at` を日付で丸めて集計する
  - スイート別は `test_run_cases.test_suite_path_content` の最上位要素で束ねる
  - 繰り返し不合格は `test_run_cases.test_case_id` で束ね、不合格となった回数の降順で返す
  - 不具合の平均解決日数は `reported_at` と `closed_at` の差から算出する（未クローズは除外する）
- `service/analytics.rs`
  - 完了予測日は、直近の実績（既定7日間）の1日あたり平均消化数から残件数を割って算出する
    - 実績が0の場合は予測を返さない（`null`）
  - 割合の分母が0になるケース（未実施のみ、対象0件）を明示的に扱う
  - 対象期間・対象バージョンの絞り込みを各集計へ渡す
- エクスポートは画面表示と同じ集計結果をCSVで返す

### フロントエンド

- テスト実行の分析画面（進捗ドーナツ、スイート別・担当者別の横棒、日別推移の折れ線、完了予測日）
- プロダクトの分析画面（バージョン別の比較、実施履歴の推移）
- 不具合の分析画面（ステータス別・重要度別、推移、平均解決日数、スイート別の発生件数）
- 繰り返し不合格ケースの一覧（テストケース詳細への導線）
- 期間・バージョンの絞り込みUIと、各画面のCSVエクスポートボタン
- グラフには件数の代替テキストを添え、色だけに依存しない表現にする
- Storybookストーリーを作成する

## テスト

- 消化率・合格率の算出（対象0件、未実施のみ、全件実施済みの各ケース）
- スイート別・担当者別・日別の集計件数
- 完了予測日（実績がない場合に `null` になること）
- 繰り返し不合格の順序と件数（複数のテスト実行にまたがる集計）
- 不具合の平均解決日数（未クローズが除外されること）
- 期間・バージョンの絞り込みが各集計へ反映されること

## 完了条件

- テスト実行・プロダクト・不具合の分析が表示でき、CSVで出力できる
- API統合テストとフロントエンドのlint・type-checkが通る

## 判断が必要な点

- **集計方式**: 集計用のテーブルやバッチは作らず、リクエストのたびにSQLで集計する。サンプルアプリのデータ量では十分で、集計テーブルの整合性を保つコストを避けるため。件数が増えた場合はインデックス追加で対応する。
- **完了予測日の算出**: 直近の実績からの単純な線形予測とする。営業日の考慮や担当者ごとの稼働率は扱わない。
- **グラフライブラリ**: 依存を増やさずSVGで描画するか、軽量なライブラリを導入するかは実装時に決める。導入する場合はフロントエンドのビルドサイズとCIのメモリ使用量に注意する。
