# スコープ08: テストケースのレビュー・承認フロー

## 目的

テストケースにレビュー工程を設け、承認済みのケースだけをテスト実行の対象にできるようにする。

## 対象要件

- テストケースは「下書き / レビュー依頼中 / 承認済み / 差し戻し」のステータスを持つ
- ユーザーは下書きのテストケースをレビュー依頼できる（レビュー担当者を指定できる）
- レビュー担当者はレビュー依頼中のテストケースを承認、または理由を添えて差し戻しできる
- 承認済みのテストケースのみテスト実行の対象にできる
- 承認済みのテストケースを変更した場合は下書きに戻る

## 前提スコープ

- 07 テストケースとテスト手順の管理

## 実施内容

### seed定義

| 種別 | 追加するもの |
| --- | --- |
| kbns | `test_case_review_action`（`request`: レビュー依頼 / `approve`: 承認 / `reject`: 差し戻し / `reset`: 下書きへ戻す） |
| entity_ids | `TestCaseReviewId` |
| entities | `test_case_review`（`id` / `test_case_id` / `action_kbn` / `acted_user_id` / `reviewer_user_id` / `comment_content` / `acted_at`） |
| tables | `test_case_reviews`（`test_case_id` にインデックス）。`test_cases` に `reviewer_user_id`（NULL許可）を追加する |
| api_schemas | `RequestReviewRequest`（レビュー担当者）、`RejectTestCaseRequest`（差し戻し理由）、`TestCaseReviewHistory` |
| api_endpoints | `POST /v1/test_cases/{test_case_id}/review_request`、`POST /v1/test_cases/{test_case_id}/approve`、`POST /v1/test_cases/{test_case_id}/reject`、`GET /v1/test_cases/{test_case_id}/reviews`、`GET /v1/test_cases/review_requests`（自分がレビュー担当のケース一覧） |
| errors | 不正なステータス遷移、レビュー担当者ではない、レビュー担当者が同一ワークスペースに所属していない、差し戻し理由が未入力 |
| pages | `TestCaseReviewList`（自分宛のレビュー依頼一覧） |

### API

- `repository/test_case_review.rs` を追加する
- `service/test_case_review.rs`
  - 状態遷移を1か所にまとめ、許可された遷移のみ受け付ける

    | 現在 | 操作 | 遷移後 |
    | --- | --- | --- |
    | 下書き / 差し戻し | レビュー依頼 | レビュー依頼中 |
    | レビュー依頼中 | 承認 | 承認済み |
    | レビュー依頼中 | 差し戻し | 差し戻し |
    | 承認済み | 内容の変更 | 下書き |

  - 承認・差し戻しは、指定されたレビュー担当者本人のみ実行できる
  - 差し戻しは理由を必須とする
  - 操作のたびに `test_case_reviews` へ履歴を追加する
- `service/test_case.rs` の更新処理を修正し、承認済みのケースが変更されたら下書きへ戻して履歴を残す
- テスト実行から参照するための「承認済みケース取得」をリポジトリに追加する（スコープ10で使用）

### フロントエンド

- テストケース詳細にステータス表示とレビュー操作（依頼・承認・差し戻し）を追加する
- レビュー履歴の表示
- 自分宛のレビュー依頼一覧画面
- Storybookストーリーを作成する

## テスト

- 各状態遷移の正常系
- 許可されていない遷移がエラーになること（例: 下書きの承認、承認済みの再承認）
- レビュー担当者以外による承認・差し戻しがエラーになること
- 承認済みケースの内容を変更すると下書きに戻り、履歴が残ること
- 差し戻し理由が空の場合にエラーになること

## 完了条件

- テストケースのレビュー依頼・承認・差し戻しが行え、状態遷移と履歴が正しく記録される
- API統合テストとフロントエンドのlint・type-checkが通る

## 判断が必要な点

- **レビュー担当者の権限**: メンバー内に権限差を設けていないため、同一ワークスペースの任意のメンバーをレビュー担当者に指定できる。自分自身を指定できるかは実装時に決める（サンプルとしては禁止する方が挙動が分かりやすい）。
- **表示順など軽微な変更の扱い**: 承認済みからの差し戻し対象を「タイトル・概要・前提条件・優先度・種別・手順」の変更に限定し、表示順や所属スイートの移動ではステータスを変更しない。
